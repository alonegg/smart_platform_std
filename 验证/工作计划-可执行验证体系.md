# 智慧教学-数据模型标准：可执行验证体系工作计划

本计划承接[平台对标研究报告](平台对标/研究报告-标准初稿可实现性与接入性评估.md)。报告结论：两平台“有没有数据”已可由源码静态对标回答；当前最大短板是标准自身尚无可机器校验的契约，第三方（尤其 AI）应用无法自证接入合格，“能否有效”“能否有帮助”尚无证据。本计划把这些短板转成可交付、可验收的工作包。

本计划及其产出均为验证材料，不修改 `标准/评审稿/`，不进入评审网站正文与下载文稿，不构成 D2 冻结、认证或符合性声明（4.4.5）。D2 冻结、待决事项裁定由标准维护机构决定；本计划只提供候选材料与证据。

## 1. 目标与成功判据

| 目标 | 对应报告问题 | 成功判据 |
|---|---|---|
| G1 契约可机器校验 | 能否有效、能否接入 | 选定子集的对象、事件、manifest 有 JSON Schema、逐事件定义、词表、正反例；正例全部通过、反例全部按预期被拒 |
| G2 校级公共服务职责可实现 | 能否实现 | 参考公共服务实现 A.8 中选定职责，契约测试通过 |
| G3 第三方可本地自测 | 能否接入 | 厂商仅凭契约包与测试工具，在本地对自己的实现执行选定 T 用例并得到可复现结果 |
| G4 平台缺口可量化 | 能否实现 | Open edX、Moodle 真实导出数据经适配器转换为契约对象，逐要素给出损失报告，并与矩阵覆盖度对照 |
| G5 AI 接入有示范 | 能否接入、能否有帮助 | 一个 AI 评分提议样例只凭契约接入，T08-P 与 T23 选定场景通过，确认请求被拒 |
| G6 效果有度量方案 | 能否有帮助、能否持续 | 试点方案、度量指标与部署脚本就绪，供学校组织真实试点 |

## 2. 范围：首批最小可行子集

首批覆盖“提交—评分—AI 提议”链路及其依赖的公共结构，这是第三方 AI 应用最常见、风险最高的接入场景；认知诊断只做最小承载与方法准入（对应 D.2.2 一期认知能力）。

| 领域 | 首批纳入 | 暂缓 |
|---|---|---|
| 公共 | 5.1 标识、ObjectRef、版本引用；Person/Organization/AcademicSession/Course/CourseVersion/Offering/Enrollment/EnrollmentRound 的最小字段；ApplicationInstance、AccessGrant | 完整主数据同步 |
| 课程资源 | Resource 版本字段（表 6-2）、RightsRecord（表 6-3）、LearningActivity、AssessmentPlan、AssessmentAdjustment、Segment（按定位类型条件字段，见 Issue #39） | 题目 QTI 全量、交互内容运行依赖 |
| 过程与证据 | 事件公共结构（表 7-1）、24 个事件（表 7-2）、TaskAttempt、Submission、ProcessArtifact、GradeProposal/GradeDecision 决定链、Feedback、PeerReview | 仿真实验专有字段 |
| 认知诊断 | CognitiveState 最小字段（表 10-1）、EvidenceLink、MethodRegistration/MethodApproval（表 10-2） | 具体诊断算法、阈值 |
| 交换 | manifest（表 8-1）、回执 | CC/QTI 全格式转换 |

适用 Profile：P-COM、P-SUB、P-GRD、P-AI，及 P-DIA 的承载部分。选定 T 用例：T01、T05、T06、T07、T08（P/C/A/R）、T09、T10、T11、T23（合成场景）、T25；T02、T14 在适配器阶段以离线包往返执行。

## 3. 统一约定（所有工作包必须遵守）

1. **目录**：全部产出在 `验证/` 下，按工作包分目录（见第 4 节）；不改 `标准/`、`designs/`、`archive/`。
2. **追溯**：每个 Schema、事件定义、测试用例都注明标准条款号和[对照矩阵](平台对标/数据要素对照矩阵.csv)要素编号；每个工作包提供“要素编号 → 产出文件”追溯表，并有脚本校验无遗漏。
3. **不发明标准**：条文未定的内容（如 E12 标识符语法、E13 摘要规范化、E14 延迟）只能作为“临时假设”，统一登记在 `验证/契约/临时假设.md`，标注对应待决事项编号和可选方案，不得写成标准要求。
4. **技术栈**：Python 3.11+；JSON Schema 2020-12；依赖仅限成熟库（`jsonschema`、`fastapi`、`uvicorn`、`httpx`、`pytest`、`pyyaml`），锁定版本；存储用 SQLite；数据交换为 UTF-8 JSON。
5. **数据**：只用合成或公开示例数据，不含真实个人信息；不提交密钥。
6. **可复现**：每个工作包有 README（目的、范围、运行命令、局限）和一条命令可跑的测试；路径用相对路径，脚本复跑不改写已提交文件。
7. **证据口径**：报告中区分“合成样例通过”“真实平台数据通过”“未执行”，按 4.4.5.2 标注证据范围。
8. **交付**：每个工作包一个 PR 到 `main`，标题前缀 `[验证/WPx]`；PR 描述列出验收清单与测试输出。
9. **标准问题回流**：工作中发现的标准歧义、遗漏或不可实现，按 `.github/ISSUE_TEMPLATE/review-comment.yml` 字段整理在工作包的 `发现的标准问题.md` 中，由负责人统一提交 Issue。

## 4. 工作包

### WP0 标准侧修订建议（不改评审稿）

- **目录**：`维护/第1轮修订建议/`
- **内容**：针对 Issue [#39](https://github.com/alonegg/smart_platform_std/issues/39)–[#47](https://github.com/alonegg/smart_platform_std/issues/47) 给出修订条文建议稿（原文、建议文本、理由、影响的表与 Profile）；待决事项 E01–E30 按 D 阶段排期表，标出阻塞本计划的项（E12、E13、E14、E22、E23a、E26）；“最小可行 Profile 组合”建议（首批厂商最少需实现哪些 Profile 与用例）。
- **验收**：9 个 Issue 均有对应建议；排期表覆盖全部待决事项；不改动 `标准/评审稿/`。
- **依赖**：无。

### WP1 候选契约包（D2 候选）

- **目录**：`验证/契约/`，子目录 `schema/`（每对象一个 Schema，共享 `common.schema.json`）、`events/`（24 个事件逐个定义：事件类型与版本、必填载荷、前置状态、接收端专属字段、AI 可否产生）、`vocab/`、`fixtures/valid/` 与 `fixtures/invalid/`（每个反例注明违反的条款）、`vectors/`（事件摘要等测试向量）、`临时假设.md`、`追溯表.csv`、`tools/validate.py`。
- **要求**：覆盖第 2 节首批子集；接收端专属字段（如 `event_id`、`auth_context`）在“发送方提交”与“接收方存储”两种视图中分别约束；AI 写入边界（只能提议、不能确认/归档）在 Schema 或事件定义中可校验；Segment 按定位类型条件必填。
- **验收**：首批子集每个对象、事件至少 1 个正例和 2 个反例；正例全过、反例全拒；追溯表覆盖首批子集全部要素编号；`python3 -m pytest 验证/契约` 通过。
- **依赖**：无（首批起点）。

### WP2 参考校级公共服务

- **目录**：`验证/参考公共服务/`
- **职责（A.8 选定项）**：事件受理（校验契约、赋值 `event_id`、按来源实例与 `source_event_id` 加摘要去重，同键不同内容进入隔离）；接收回执；按应用实例生成学习者假名与映射；AccessGrant 签发、校验、撤销与传播；用户委托访问与客户端凭证的区分；评分决定链状态机（提议→确认→归档→更正，服务身份不得确认）；方法登记、用途批准、暂停与运行时准入校验；审计日志。
- **接口**：HTTP JSON，提供 OpenAPI 文件 `openapi.yaml`；认证用本地签发的测试令牌（模拟 OAuth2 客户端凭证与委托访问），不对接真实统一身份认证。
- **验收**：所有入站数据用 WP1 Schema 校验；单元与接口测试覆盖上列职责的正反路径；一条命令启动（`uvicorn` 或 docker compose）。
- **依赖**：WP1。

### WP3 符合性测试工具

- **目录**：`验证/测试工具/`
- **内容**：命令行 `validate`（校验任意 JSON/包是否符合契约）；T 用例执行器，以“被测实现地址 + 角色声明（Profile）”为输入，按 A.6 表 A.9 选择用例，对选定 T 用例逐条执行，输出机器可读结果与人可读报告（通过/失败/不适用及理由）；用例数据放 `cases/Txx/`（输入、预期、反例）。
- **验收**：对参考公共服务执行 T05、T06、T07（可模拟部分）、T08-P/C/A/R、T09、T10、T11、T25 全部得出结论；故意注入缺陷的“坏实现”能被对应用例判失败（至少 5 类缺陷）。
- **依赖**：WP1、WP2。

### WP4 平台数据适配与损失量化

- **目录**：`验证/平台适配/openedx/`、`验证/平台适配/moodle/`
- **WP4a 取样**：用 Docker（Moodle 官方镜像、Open edX Tutor）部署固定版本（与[对标 README](平台对标/README.md) 的源码快照一致或记录差异），用合成课程与合成学员产生真实导出：Open edX 课程 OLX 导出与 tracking log/xAPI 输出；Moodle 课程备份 .mbz、日志与成绩历史；记录版本与步骤，样本存入 `samples/`（只含合成数据）。
- **WP4b 转换**：把样本转换为 WP1 契约对象与事件；逐要素损失报告（成功、有损、无法生成及原因）；与矩阵覆盖度对照，指出静态判断被推翻的项。离线执行 T01、T02（包往返）与 T14（第二应用读取历史资产）的数据部分。
- **验收**：转换输出全部通过 WP1 校验；损失报告覆盖首批子集全部要素；与矩阵的差异有说明。
- **依赖**：WP4a 无依赖；WP4b 依赖 WP1。

### WP5 AI 接入样例

- **目录**：`验证/AI接入样例/`
- **内容**：声明 P-AI + P-GRD（仅提议）的评分提议应用。通过 AccessGrant 读取作品与量规，生成带方法版本与来源的评分提议，写入参考公共服务；默认用确定性规则评分器，可选接入大模型（密钥由环境变量提供，不提交）；附带接入说明，演示厂商如何只凭契约完成接入。
- **验收**：用 WP3 执行 T08-P、越权确认反例、T11、T23 选定合成场景（直接与间接提示注入、越权工具调用）全部通过；尝试确认、归档请求被拒并有审计。
- **依赖**：WP1、WP2；建议在 WP3 完成后验收。

### WP6 试点与度量方案

- **目录**：`验证/试点方案/`
- **内容**：试点课程选择标准；师生任务（T16、T26）脚本；度量指标（教师评分与反馈耗时、提议采纳与修改率、学生复核与更正量、接入工作量人日、故障与撤权演练结果）；伦理与个人信息处理要点（对应 D3）；部署与回收清单。
- **验收**：指标有定义、采集方式与基线；与 D3/D4 放行条件对应。
- **依赖**：无；真实试点由学校组织，不在本计划自动执行范围。

## 5. 排程与派工

| 批次 | 并行工作包 | 前置 | 预计 |
|---|---|---|---|
| 第 1 批 | WP0、WP1、WP4a、WP6 | 无 | 1–2 周 |
| 第 2 批 | WP2、WP4b | WP1 合并 | 1–2 周 |
| 第 3 批 | WP3、WP5 | WP2 合并 | 1–2 周 |
| 第 4 批 | 汇总：全部用例联跑，更新研究报告五问结论与证据等级 | 第 3 批合并 | 3–5 天 |

每个工作包由独立子会话完成，产出 PR；负责人逐个审查 PR（对照本计划验收条款与第 3 节约定），合并后再派下一批。

## 6. 风险与应对

| 风险 | 应对 |
|---|---|
| 条文未定导致契约无据 | 只记临时假设并回流 Issue，不擅自定标准 |
| 子会话之间约定不一致 | 全部以 WP1 的 `common.schema.json` 与本计划第 3 节为准；后续工作包发现契约问题时提 PR 修改 `验证/契约/` 并说明 |
| 平台部署失败或版本漂移 | 记录版本与失败步骤；退回用官方示例导出包，并在报告中降级证据等级 |
| 合成数据通过被误读为真实有效 | 报告严格区分证据等级；“能否有帮助”只能由 WP6 试点回答 |
| 契约体量过大 | 首批只做第 2 节子集，其他按后续批次扩展 |

## 7. 完成后对五问结论的预期影响

| 问题 | 当前 | 本计划完成后可达到 |
|---|---|---|
| 能否实现 | 有条件成立 | 有合成与真实导出数据证据（首批子集） |
| 能否有效 | 尚无证据 | 契约可校验、用例可执行（合成证据） |
| 能否持续 | 有条件成立 | 不变；需学校落实维护岗位与待决事项 |
| 能否接入 | 有条件成立 | 有第三方自测工具与 AI 接入示范 |
| 能否有帮助 | 尚无证据 | 有度量方案；结论待真实试点 |
